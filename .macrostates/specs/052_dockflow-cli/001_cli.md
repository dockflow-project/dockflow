# Shared CLI contract

## Root interface

The shared CLI is a minimal command host. Its initial root interface consists
of `--help`, `--version`, and installed module groups:

```text
dockflow
dockflow --help
dockflow --version
dockflow pipelines --help
dockflow pipelines run ...
```

Bare `dockflow` displays root help and exits with code 0. `--help` also prints
help and exits 0. Root help lists installed module groups in deterministic name
order with their supplied descriptions. With no feature packages installed,
display useful help and explain that installing a feature package into this
Python environment adds command groups; do not query a registry or install it.

Root `--version` prints `dockflow <version>` using the installed `dockflow-cli`
distribution version and exits 0. Handle this before feature discovery/loading,
so it works with broken feature plugins. Missing distribution metadata produces
an actionable installation error and exit 1; do not invent a version or read an
untracked/local `VERSION` fallback. Root options precede the module word; options
inside a module's command tree belong to that module.

Keep Typer's automatic shell-completion installation options disabled for the
initial root interface. Command parsing otherwise follows the selected Typer
behavior unless this contract specifies an observable difference.

## Ownership and registration

The public command structure is `dockflow <module> <command> [options]`.
`dockflow-cli` alone owns the `dockflow` executable. Functional distributions
register Typer applications through the `dockflow_cli.modules` entry-point group.
The entry-point name supplies the public module word, and its target resolves to
a `typer.Typer` instance. Use `dockflow_cli.main:main` as the shared console-script
target. Each tool owns its module name, exported application, and command tree;
the concrete Pipelines registration is recorded in its own specification.

Feature distributions depend on a compatible `dockflow-cli`; the CLI must not
depend on feature modules or import KFP and Docker to assemble root help.
Packages that import Typer must declare it directly. Command handlers delegate
to application logic instead of duplicating orchestration.

Use standard-library `importlib.metadata.entry_points` with group
`dockflow_cli.modules`. Discover installed distributions in this same Python
environment; do not scan repository directories, infer plugins from distribution
names, search other environments, or require a server-side plugin registry.
Installing/removing a valid feature distribution changes the available groups
on the next invocation without changing or rebuilding the shared CLI.

Each entry point contributes one root group. Its value is an importable object
reference, conventionally `<import_package>.cli:app`, exporting a `typer.Typer`
instance. Factories, arbitrary callables, custom host subclasses, and private
CLI imports are not part of the initial registration API. Providers may expose
several groups through distinct entry points; the initial first-party Pipelines
package exposes only `pipelines`. Third-party providers use the same contract
and declare their compatible host/Typer requirements in distribution metadata.

## Names, discovery, and failures

Module names use lowercase ASCII words/numbers separated by single hyphens:
`^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`. Reserve `help` and `version` at the root.
Reject invalid names, reserved names, duplicate names across providers, and
collisions with any built-in command. Do not silently normalize a name or choose
a winning provider. Report the conflicting entry points and distributions.

Inventory and validate names/collisions before loading providers. Sort entries
by module name, with provider identity and target as deterministic secondary
keys for diagnostics. Load all valid registrations eagerly, then mount their
applications using the entry-point names. A bad import, incompatible application
object, or command-construction failure stops normal startup with exit 1 and an
actionable module/provider diagnostic. Do not silently omit a broken module or
continue with partial discovery. Root `--version` retains its independent path.

Entry points execute trusted installed Python code. Registration is an extension
contract, not process isolation or a sandbox.

## Observable behavior

Root help lists installed module groups. Group help lists its commands. Help and
CLI construction must not start services, execute pipelines, contact a server,
or connect to Docker, object storage, or a database. Defer heavyweight execution
imports until needed by a command.

All help/version requests are side-effect-free. Plugin authors must keep their
exported application import/assembly lightweight; the host cannot make arbitrary
plugin code safe by loading it. Explicit command execution owns runtime work.

## Output, errors, and configuration

Send normal results, help, and version output to stdout. Send diagnostics and
usage errors to stderr. Exit 0 on success, 1 on operational/startup failure,
and 2 on invalid command usage such as an unknown module, bad option, or missing
required argument. Preserve the underlying command's deliberate exit result
under these conventions; the host must not convert a failed command to success.
Unexpected exceptions receive a concise diagnostic and exit 1, without a raw
traceback by default. Required plugin failure messages identify the module and
provider. A startup failure can prevent help/dispatch until the installation is
repaired; it does not prevent standalone root version reporting.

The host introduces no global configuration file, endpoint setting, plugin
enable/disable registry, or shared tool-options namespace. Feature settings,
environment variables, authentication, structured output options, and execution
arguments belong to their tool package. Package installation remains with
Python packaging tools. Add shared configuration or root commands only through
deliberate specification work when a concrete shared need exists.

Do not add aliases for an unreleased flat command interface. Do not invent
tool command arguments while that tool's runtime contract remains incomplete.

Packaging identities, dependency selection, and required verification are owned
by [Packaging and verification](002_packaging-and-verification.md).
